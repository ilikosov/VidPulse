# ADR 0007: Хранилище превью видеофайлов — кадры как BLOB в БД

- **Status:** Accepted
- **Date:** 2026-07-17
- **Owners:** Backend team
- **Tags:** files, media, storage, previews
- **Related:** `apps/server/src/services/file.service.ts`, `apps/server/src/services/file-thumbnail.service.ts`, `packages/db/migrations`

---

## 1) Context

Превью видеофайлов в редакторе файлов были **эфемерными**: `GET /api/files/:id/thumbnails` при
каждом открытии дровера заново запускал ffmpeg, извлекал 3 кадра во временную папку, отдавал их как
base64 data URI и сразу удалял temp-dir. Ничего не сохранялось — превью не переживали закрытие
дровера, а каждое открытие тратило CPU на повторную генерацию.

Потребовалось **постоянное хранилище картинок**: генерировать превью по явному действию
пользователя (кнопка в редакторе), складывать результат в хранилище и показывать из него.

## 2) Decision

**Превью хранятся строками в новой таблице `file_previews`** (миграция
`20260717000000_create_file_previews_table.ts`): `file_id` (FK → `files`, `ON DELETE CASCADE`),
`position` (порядок кадра), `image` (сырые байты JPEG, BLOB), `created_at`; уникальность
`(file_id, position)`.

- **Генерация — по кнопке.** `POST /api/files/:id/thumbnails` → `fileService.generatePreviews`:
  извлекает кадры (`generateThumbnailBuffers`, ffmpeg), сохраняет их
  (`fileRepository.replacePreviews` — атомарная замена всего набора для файла), возвращает свежие
  кадры как data URI.
- **Чтение — из хранилища.** `GET /api/files/:id/thumbnails` → `fileService.getThumbnails` читает
  сохранённые байты (`fileRepository.getPreviews`) и кодирует в data URI. ffmpeg на GET не
  вызывается. Формат ответа `{ thumbnails: string[] }` не изменился — фронтенд рендерит те же data
  URI через `<Image.PreviewGroup>`.

**Почему БД, а не папка на диске + статика.** Рассматривались два варианта хранилища: (а) таблица с
BLOB; (б) каталог на диске (`THUMBNAIL_DIR`) + `express.static`. Выбран (а):

- **Самодостаточность.** Всё состояние приложения — один SQLite-файл; не нужны новый env, каталог с
  правами на запись и статический middleware (сейчас сервер не раздаёт файлы вовсе).
- **Каскадная очистка.** FK `ON DELETE CASCADE` удаляет превью вместе со строкой `files` — нет
  осиротевших файлов на диске, нет ручной уборки.
- **Малый объём.** 3 JPEG-кадра на файл (десятки КБ каждый) — приемлемая нагрузка на SQLite.

## 3) Consequences

- **+** Превью сохраняются между сессиями; повторное открытие дровера не перезапускает ffmpeg.
- **+** Единый источник правды и транзакционная согласованность (замена набора в транзакции).
- **+** Нет новой инфраструктуры раздачи статики/каталогов/env.
- **−** Двоичные данные в БД увеличивают её размер и попадают в дампы/бэкапы; для больших наборов
  превью это стало бы неудобным. Если в будущем понадобятся крупные/многочисленные изображения —
  мигрировать на диск + статику (интерфейс репозитория это скрывает: меняется реализация
  `getPreviews`/`replacePreviews`, не вызывающий код).
- **−** data URI дублируют байты в JSON-ответе (base64 ≈ +33%); для 3 маленьких кадров несущественно.
