# ADR 0002: Разделение «сырого парсинга» и канонических ссылок (устранение двойного источника истины)

- **Status:** Accepted (решение принято; реализация в коде/схеме — отдельная future-работа)
- **Date:** 2026-06-03
- **Owners:** Backend team
- **Tags:** database, dictionary, metadata, denormalization, parser
- **Related:** [ADR 0001](./0001-canonical-dictionary-entities.md)

> **Scope этого документа:** фиксируется только **проектное решение** (целевая структура данных и поведение).
> Код и схема в рамках этого ADR **не меняются**. Реализация и миграции — отдельным PR по плану ниже.

## 1) Context

В таблице `videos` метаданные перформанса хранятся **дважды**:

- денормализованные текстовые поля: `group_name`, `artist_name`, `song_title`, `event`;
- канонические ссылки (FK) на словарь: `group_id`, `artist_id`, `song_id`, `event_id`.

Текущий резолвер `src/services/parser/metadataResolver.service.ts` (строки ~106–109) при совпадении со словарём **перезаписывает текстовое поле каноническим именем**, а при отсутствии совпадения — оставляет результат парсинга:

```ts
group_name: group ? group.canonical : groupInput || null,
group_id:   group?.id ?? null,
```

То есть в одной колонке `group_name` смешаны **три разных понятия**:

1. **результат парсинга** (что распознали; evidence);
2. **каноническая ссылка** (`group_id` — совпадение со словарём);
3. **отображаемое значение** (`канон ?? парсинг`).

### Проблемы

- **Рассинхрон при переименовании.** Запись в `dictionary_groups` переименовали → `videos.group_name` хранит устаревшую копию, хотя `group_id` указывает на ту же (уже переименованную) запись.
- **Потеря результата парсинга.** При совпадении исходная распознанная строка затирается каноникой и недоступна для ре-резолва, ревью и обучающих данных.
- **Дублирование** имён словаря в каждой строке `videos`.
- **Хрупкие чтения.** `src/services/dictionary.service.ts` джойнит по тексту и по `OR`:
  - строка ~404: `ON v.group_id = g.id OR v.group_name = g.name`;
  - `getVideosByField` (строка ~596): `LEFT JOIN dictionary_groups dg ON videos.group_name = dg.name`.

---

## 2) Decision (Вариант 1)

Принимается следующая целевая модель для `group` / `artist` / `event`:

1. **Текстовые поля `group_name` / `artist_name` / `event` хранят ТОЛЬКО результат парсинга.**
   Их **никогда** не перезаписываем каноническим значением из словаря.
2. **FK-поля `group_id` / `artist_id` / `event_id` — единственный источник «совпало со словарём».**
3. **Отображаемое значение не хранится, а выводится на чтении** по правилу
   **«приоритет у словаря, иначе результат парсинга»**:

   ```sql
   COALESCE(dg.name, videos.group_name) AS group_display
   ```

   Логика централизуется в одном месте — SQL-VIEW `videos_display` (или единый query-хелпер), а не размазывается по запросам.

4. **Резолвер перестаёт перезаписывать текст**: пишет сырой парсинг в текстовое поле и `*_id` в FK:

   ```ts
   group_name: groupInput || null,   // всегда сырой парсинг
   group_id:   group?.id ?? null,    // каноническая ссылка
   ```

### Песни (важная оговорка)

Песен у видео может быть несколько, поэтому одиночные `videos.song_id` / `videos.song_title` концептуально не подходят. В рамках **этого** решения песни **остаются как есть** (canonical-набор в `video_songs`, см. [ADR 0001 / Update](./0001-canonical-dictionary-entities.md)), а `videos.song_id` / `song_title` сохраняются как legacy dual-write.

Целевое расширение (отдельная future-работа): добавить в `video_songs` поля `raw_title` (результат парсинга), nullable `song_id` (канон) и `position`, тогда отображение песни = `COALESCE(ds.title, raw_title)`, что закрывает и кейс несопоставленных песен.

## 3) Consequences

### Positive

- Переименование записи в словаре отражается **мгновенно** (нет staleness).
- Сохраняется **результат парсинга** — доступен для ре-резолва, ревью и `training_data`.
- Уходит **дублирование** канонических имён в строках `videos`.
- Джойны становятся **чисто по FK** — убираются хрупкий `OR`-джойн и текст-джойн.
- Чёткая семантика колонок: текст = evidence, FK = канон, display = производное.

### Negative / Trade-offs

- Каждое отображение требует `LEFT JOIN` к словарю (на практике он уже почти везде есть).
- Составной индекс `videos_perf_meta_idx` по текстовым полям нужно пересмотреть: часть фильтров переедет на `*_id`.
- Разовый рефактор read-path (роуты/сервисы) и связанных тестов.

### Risks

- При backfill нужно **не потерять** исходный парсинг: до миграции текстовое поле могло уже содержать каноническое имя, а не распознанную строку (исторические записи). Восстановление «истинного» парсинга для них невозможно — для них текст останется = канон на момент backfill (приемлемо как нижняя граница).
- Фронтенд и любые внешние потребители, читающие `group_name` напрямую, должны перейти на display-поле из VIEW/хелпера.

## 4) Implementation plan (future PR, не выполняется здесь)

1. **Схема**
   - Решить судьбу `videos_perf_meta_idx` (оставить по тексту для поиска / заменить индексами по `*_id`).
   - Добавить VIEW `videos_display` с `COALESCE(dict, raw)` по всем четырём полям (event с учётом `@`-нормализации).
2. **Резолвер** (`metadataResolver.service.ts`)
   - Убрать перезапись: `*_name` ← сырой парсинг, `*_id` ← резолв.
3. **Read-path** (`dictionary.service.ts`, роуты)
   - Заменить `OR`-джойн (стр. ~404) и текст-джойн `getVideosByField` (стр. ~596) на FK-джойны.
   - Перевести чтение/сериализацию видео на `videos_display` / хелпер.
4. **Backfill (идемпотентный)**
   - Зафиксировать текущее поведение как baseline; для строк, где текст уже равен канонике, изменений нет.
5. **Фронтенд**
   - Читать display-поле вместо «сырых» `*_name`.
6. **Тесты**
   - Обновить unit/e2e: проверка, что после переименования словаря display меняется, а текст-evidence — нет.

## 5) Rollback strategy

- Решение пока **только документационное** — откат тривиален (удалить ADR).
- На этапе реализации: VIEW и FK-джойны аддитивны; быстрый runtime-rollback — вернуть чтение на текстовые поля; перед удалением/переименованием колонок — backup и отдельный destructive-шаг (по аналогии с [ADR 0001 §5](./0001-canonical-dictionary-entities.md)).
